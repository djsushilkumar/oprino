## 1. Traceability Framework & Strict Status Definitions

To eliminate false claims of readiness, every owner-approved decision from the original 65-decision sequence is tracked individually across six rigid status columns. No column may be inferred from another:

1. **Approved:** Formally confirmed by the Product Owner in the original 65-decision execution pack.
2. **Documented:** Fully specified with operational rules and data contracts in [`OPRINO-MASTER-PRD-V2.md`](./OPRINO-MASTER-PRD-V2.md), [`OPRINO-TECHNICAL-ARCHITECTURE-V2.md`](../architecture/OPRINO-TECHNICAL-ARCHITECTURE-V2.md), [`CONFLICT-REGISTER.md`](./CONFLICT-REGISTER.md), or numbered ADRs.
3. **Implemented:** Working code written in active repository modules (`services/api`, `services/worker`, `packages/database`, `apps/web`, `apps/mobile`).
4. **Tests Passed:** Verified by automated unit, integration, or mobile widget tests (distinguishing local working branch execution from remote CI runs).
5. **Staging / Hardware:** Verified on physical OEM test hardware (e.g. OnePlus CPH2707IN) or deployed staging container environment.
6. **Production:** Fully deployed, verified, and active on live production cloud infrastructure (e.g. Render API, Vercel Web, Neon PostgreSQL).

## 3. Actual Local Database Schema Verification (Q14 & Q49)

### 3.1 Q14 Verification: Account-to-Company Tenancy Constraint
- **Local Source Files:** [`packages/database/src/schema/users.ts`](../../packages/database/src/schema/users.ts) and [`packages/database/src/schema/tenants.ts`](../../packages/database/src/schema/tenants.ts).
- **Actual Schema Reality:**
  1. The `users` table does **NOT** have a `workspace_id` column. It is a global identity table (`id`, `name`, `email`, `status`).
  2. Workspace associations are modeled exclusively through the `workspace_memberships` table in `tenants.ts`.
  3. `workspace_memberships` has a compound unique constraint: `unique('workspace_memberships_workspace_user_idx').on(table.workspaceId, table.userId)`. This ensures a user can only belong once to a *given* workspace, but does **NOT** prevent a single user ID from being associated with *multiple* distinct workspaces.
  4. The `sessions` table in `users.ts` explicitly includes `activeWorkspaceId: uuid('active_workspace_id')`, which allows a session to switch or track an active workspace among multiple memberships.
  5. In [`services/api/src/routes/auth.ts:L228–243`](../../services/api/src/routes/auth.ts#L228-L243), user sign-in executes `SELECT workspace_id FROM workspace_memberships WHERE user_id = :userId AND status = 'active' LIMIT 1;`.
- **Verdict:** The approved policy **Q14 — Each user account belongs to one company** is **NOT YET IMPLEMENTED**. To enforce this invariant in Phase 2, a migration must either add a unique constraint on `workspace_memberships.user_id` alone or add an explicit check rejecting invites/signups if an email already belongs to any active workspace membership.

### 3.2 Q49 Verification: Retention Schema Field & Safe Migration Proposal
- **Local Source Files:** [`packages/database/src/schema/tenants.ts`](../../packages/database/src/schema/tenants.ts) and [`services/worker/src/worker.ts`](../../services/worker/src/worker.ts).
- **Actual Schema Reality:**
  1. In `tenants.ts:L23`, the field `location_retention_days` **ALREADY EXISTS** on the `workspaces` table:  
     `locationRetentionDays: integer('location_retention_days').notNull().default(30),`
  2. In `worker.ts:L48` and `L63`, the retention prune worker (`telemetry.retention.prune`) already queries `location_retention_days` per workspace and passes it to `telemetry_prune_workspace_records`. However, its fallback default is currently `30`.
- **Safe Migration Proposal (Phase 2 — Zero Database Modifications in Phase 0):**
  1. **Schema Definition Update:** Update `tenants.ts` Drizzle schema default from `.default(30)` to `.default(90)`.
  2. **Database Migration Script:** Generate a safe migration:  
     ```sql
     ALTER TABLE workspaces ALTER COLUMN location_retention_days SET DEFAULT 90;
     ```
  3. **Worker Fallback Update:** In `services/worker/src/worker.ts`, update line 48 and line 63 fallback value from `30` to `90`:  
     `const retentionDays = ws?.location_retention_days ?? job.data?.retentionDays ?? 90;`
  4. **API Route Validation:** In `services/api/src/routes/workspaces.ts` (and Zod contract in `packages/contracts`), update workspace settings schema validation to allow only `[30, 90, 180]` (deprecating the old unapproved `7` option).
  5. **Existing Tenant Policy:** Existing workspaces with `30` remain unaffected unless updated by the tenant administrator via workspace settings.
